# 共通ルール

## 言語
- かならず日本語でやり取りする

## Git
- Git 操作（commit / push / branch 等）はユーザーが行う。Claude は実行しない

## 作業の進め方
- 不明点や前提が曖昧なときは推測で進めず確認する
- 指示外のリファクタ・スコープ拡大・ファイル新規作成（README 等の自動生成を含む）をしない
- `rm` などの破壊的・不可逆な操作は実行前に確認する

## 機密情報
- API キー・トークン・パスワード・`.env`・秘密鍵をコミットしない／チャットやログに出力しない
- 値を示す必要があるときはプレースホルダ（`<API_KEY>` 等）で書く

## コミットメッセージ
- Conventional Commits: `type: 説明`。type は英語、説明は日本語
- type: feat / fix / refactor / perf / test / docs / build / chore
- 破壊的変更は `type!:`（例: `refactor!: CLI 引数整理`）
- 件名は「何をしたか」を簡潔に。Claude は commit せず、この形式でメッセージ案を出す

## コーディング
- 型は厳格に。strict 設定を有効化し、型アノテーションを省略しない（言語別の詳細は各プロジェクトの CLAUDE.md）
- 1ファイル 400 行 / 1関数 50 行を目安に。超えそうなら分割を検討（行数より「1ファイル1責務」を優先）
- 変更後はフォーマッター/リンターを実行してから完了とする（使うコマンドはプロジェクト設定に従い、推測しない）

### コメント
- 言語は日本語で簡潔に。「なぜ / 何を」を書く（自明な What の単純な繰り返しは避ける）
- 関数・メソッド: ブロック形式の JSDoc で開く（`/**` で改行して書く）。冗長な Args / Return は書かない
- 型のプロパティ / メンバ: ワンライナー JSDoc（`/** ... */` を一行で）
- 処理中の説明: 通常コメント（`//`）で記載
- 文末に句点「。」は付けない
- 「なぜ / 何を」を述べてから関連する処理を一塊で書き、次の処理塊との間は一行空ける

## 依存
- 新しい依存を入れる前に、標準ライブラリ/既存依存で代替できないか検討する。採用するなら理由（なぜ自前実装や軽量手段でダメか）を添える。重い依存は特に警戒する

## 設計
- 依存方向は上位→下位の一方通行（UI → サービス → データアクセス）。逆参照禁止
- 新ファイルは既存の同種ファイルと同じディレクトリへ。新ディレクトリを作る前に既存構造を確認

## テスト
- 対象はロジック層（services / lib / utils）。UI コンポーネントの描画テストは原則やらない

### 命名（describe/it 形式）
- ケース名は基本形 `<条件>のとき<結果>` で書く
  - 条件は「〜のとき」で統一する
  - 否定・欠落は「<対象>なしのとき」「<対象>不統一のとき」「<項目>欠落のとき」「<対象>が見つからないとき」のように表す
  - 結果は動詞で終える（「xxx を返す」「例外を投げる」「xxx を呼ぶ」「保存する」「許可する」）
  - 単体関数が主語のときは「<関数名>は〜する」とする

## Knowledge DB（~/.claude/knowledge/）
プロジェクト横断の長期知識を md で蓄積（Auto Memory はプロジェクト内の短期記憶、こちらは横断的な長期知識）。

- 検索: 過去に扱った可能性がある話題は、関連しそうなときだけ Grep で `~/.claude/knowledge/` を引く
- 記録: 次の知見が出たらその場で残す — 調査結果(qa) / 設計・技術選定の判断(decision) / ハマりと解決(pitfall) / 再利用パターン(pattern) / 未着手の検討(todo)
- 形式: `~/.claude/knowledge/YYYY-MM-DD_タイトル.md`、INDEX.md に1行リンクを追記
- フロントマター: `category`（上記5種） / `project`（グローバルなら省略） / `tags`（カンマ区切り）
