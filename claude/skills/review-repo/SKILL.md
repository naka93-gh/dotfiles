## 対象

リポジトリ内の主要ソースを「全体」として読む。ベンダー・ビルド成果物は除外:
`target/` `dist/` `build/` `node_modules/` `.git/` `coverage/` など。

## 把握フェーズ

まずリポジトリの形を掴む:

1. !`git ls-files | wc -l` で総ファイル数
2. !`git ls-files | head -80` で構成を確認（必要なら範囲を広げる）
3. `README.md` / `CLAUDE.md` / `AGENTS.md` を Read し、設計方針・依存方向ルール・サイズ規約を把握
4. 大きいファイルを抽出: !`git ls-files | xargs wc -l 2>/dev/null | sort -rn | head -20`
5. 必要に応じて主要モジュール（エントリ、ドメイン中核、共通基盤）を Read

## レビュー観点

差分用 rule-review skill の観点（ルール準拠・設計・ロジック・セキュリティ）に加え、全体だからこそ見える項目を重視する:

### 1. 構造・依存

- ディレクトリ構造が `CLAUDE.md` の設計方針と一致しているか
- 依存方向の逆流（下位レイヤから上位レイヤへの import）が無いか
- モジュール責務の重複・分散・凝集の崩れ

### 2. ファイルサイズ

- 400 行を超えるファイルを列挙し、分割の必要性を判断する

### 3. 一貫性

- 命名規則の揺れ（snake/camel 混在、用語のブレなど）
- 同じ目的の処理が複数の書き方で実装されている
- エラー型・ログ・I/O 抽象のパターン統一

### 4. デッドコード・古い痕跡

- 参照されていない公開関数・型・モジュール
- 古い `TODO` / `FIXME` / コメントアウトされたコード

### 5. テストの薄い領域

- ロジック層（services / lib / utils 相当）でテスト未整備のファイル
- カバレッジが偏っている領域

### 6. ルール違反 / セキュリティ

- `CLAUDE.md` のルール（型厳格、依存方向、1ファイル 400 行 / 1関数 50 行、依存追加の妥当性）
- 言語固有ルール（`rules/*.md`、例: SQL の CTE）は、プロジェクトが採用していれば確認する
- 機密情報（API キー・トークン・鍵）のハードコードや出力露出、インジェクションリスク

## 出力フォーマット

観点別にカテゴリ分けし、各指摘は以下の形式:

```
## <カテゴリ>

- [重要度: 高/中/低] 指摘内容
  - 該当: <ファイルパス>[:行]
  - 理由: なぜ問題か
  - 提案: どう直すか
```

最後に「全体総評」を 3〜5 行で書く（強み / 主要リスク / 次の打ち手）。

## 役割分担

- 作業中差分のレビューは `rule-review` skill を使う（このスキルは差分を見ない）
- ドキュメントとコードの齟齬は `docs-check` skill が拾う（重複する観点はそちらに譲ってよい）
