ブランチが最終的に持ち込む変更を、読み込まれているルールと既存の設計に照らしてレビューする。
コミット単位ではなく、base との差分全体を見る。

## base の決定

引数 `$ARGUMENTS` があれば、それを base にする。無ければ次で判定する。

- !`git symbolic-ref --quiet --short refs/remotes/origin/HEAD 2>/dev/null || echo "(origin/HEAD 未設定)"`
- !`git branch --format='%(refname:short)'`
- !`git rev-parse --abbrev-ref HEAD`

`origin/HEAD` が取れればそれを使う。取れない場合はブランチ一覧から既定ブランチを推定し、**どれを base にしたかを出力の冒頭に明記する**。
`main` と決め打ちしない。判断できなければユーザーに尋ねて止まる。

現在のブランチが base 自身なら、その旨を伝えて終了する。

## 差分の取得

base を決めてから規模を見る。

```
git diff --stat <base>...HEAD
git log --oneline <base>..HEAD
```

差分が無ければ「base との差分なし」と伝えて終了する。

規模に応じて読み方を変える。差分全体を無条件に読み込まない。

- 小さければ `git diff <base>...HEAD` をまとめて読む
- 大きければ `git diff --name-only <base>...HEAD` で一覧を取り、`git diff <base>...HEAD -- <path>` でファイル単位に読む

## レビュー観点

### 1. ルール準拠

読み込まれているルール（プロジェクトの `CLAUDE.md` と `.claude/rules/`）に照らして違反を探す。
このスキルは規約を再定義しない。ルールに書かれていないことを違反として挙げない。

### 2. 設計

- 責務の分離は適切か（1つの関数・クラスが複数の責務を持っていないか）
- 既存のコードとパターンが統一されているか
- 不要な抽象化や過度な複雑さがないか

### 3. ブランチとしての妥当性

- 1つのブランチに複数の目的が混ざっていないか。混ざっていれば分割を提案する
- 途中で入れて後から不要になった変更、デバッグ用のコードやコメントアウトが残っていないか
- 一時ファイル・自動生成物・ロックファイルの意図しない混入がないか

### 4. 明白な欠陥のみ

- null / undefined の未処理、off-by-one、エッジケースの考慮漏れ
- インジェクション（SQL / XSS / コマンド）、機密情報の露出

網羅的なバグ・効率のレビューは深追いせず、ビルトイン `code-review` に委ねる。
コメントやテスト名の体裁は `format-check` の担当。

## 出力フォーマット

冒頭に base とコミット数を1行で書く。指摘はファイル単位でまとめる。

```
base: <base ブランチ>（<N> commits / <M> files）

## <ファイルパス>

- [重要度: 高/中/低] 指摘内容
  - 該当箇所: L行番号
  - 理由: なぜ問題か
  - 提案: どう直すか
```

最後に全体の総評を1〜2文で書く。指摘が無ければ「問題なし」と明記する。
