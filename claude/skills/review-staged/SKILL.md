staged の内容が、読み込まれているルールと既存の設計に沿っているかをレビューする。
staged には自分の作業だけでなく、ブランチを squash した大きな差分が載ることもある。規模を見てから読み方を決める。

## 差分の取得

まず規模だけを見る。

- !`git status --short`
- !`git diff --cached --stat`

staged が空なら「staged なし」と伝えて終了する。unstaged は対象にしない。

規模に応じて読み方を変える。差分全体を無条件に読み込まない。

- 小さければ `git diff --cached` をまとめて読む
- 大きければ `git diff --cached --name-only` で一覧を取り、`git diff --cached -- <path>` でファイル単位に読む

## レビュー観点

### 1. ルール準拠

読み込まれているルール（プロジェクトの `CLAUDE.md` と `.claude/rules/`）に照らして違反を探す。
このスキルは規約を再定義しない。ルールに書かれていないことを違反として挙げない。

### 2. 設計

- 責務の分離は適切か（1つの関数・クラスが複数の責務を持っていないか）
- 既存のコードとパターンが統一されているか
- 不要な抽象化や過度な複雑さがないか

### 3. スコープ

- 変更が目的の範囲に収まっているか（無関係なリファクタ・自動生成物が混ざっていないか）
- squash 由来で複数の目的が混ざっている場合は、分割を提案する

### 4. 明白な欠陥のみ

- null / undefined の未処理、off-by-one、エッジケースの考慮漏れ
- インジェクション（SQL / XSS / コマンド）、機密情報の露出

網羅的なバグ・効率のレビューは深追いせず、ビルトイン `code-review` に委ねる。
コメントやテスト名の体裁は `format-check` の担当。

## 出力フォーマット

指摘はファイル単位でまとめる。

```
## <ファイルパス>

- [重要度: 高/中/低] 指摘内容
  - 該当箇所: L行番号
  - 理由: なぜ問題か
  - 提案: どう直すか
```

最後に全体の総評を1〜2文で書く。指摘が無ければ「問題なし」と明記する。
