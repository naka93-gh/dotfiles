コメント規約とテスト命名規約への違反を点検する。確定的な違反はその場で修正し、内容の判断・推測が要るものは修正案として提示する（創作で埋めない）。
見るのは「形式・体裁が規約どおりか」だけで、コードとドキュメントの内容齟齬や設計の妥当性は扱わない。

## 点検する規約

読み込まれているルール（プロジェクトの `CLAUDE.md` と `.claude/rules/`）を正とする。
このスキルは規約を再定義しない。規約が見当たらなければ、その旨を伝えて終了する。

対象は次の2種類に限る。

- コメント規約（コメントの言語・形式・配置・JSDoc のタグ）
- テスト命名規約（`it` / `test` のラベル）

## 対象の取得

引数でパス / グロブを受け取れる。無ければ作業中の変更ファイルを対象にする（点検範囲を限定し、無関係な箇所を触らない）。

```bash
git status --short
git diff --name-only
git diff --cached --name-only
```

「全体」と明示された場合のみリポジトリ全体を対象にする（`node_modules/` `dist/` `build/` `target/` 等は除外）。
対象が無ければ「点検対象なし」と伝えて終了する。

## 修正の方針

各ファイルを Read し、違反を 2 種に仕分ける。

### 自動修正する（確定的・意味を変えない）

以下はよくある違反の例。ルールに該当する項目が無ければ、その項目は点検しない。

- 文末の句点「。」を除去する
- 関数・メソッド上の行コメント（`//`）を、ブロック JSDoc（`/** ... */`）へ変換する
- 型のプロパティ / メンバに付いた複数行 JSDoc を、内容そのままワンライナーへ畳む
- 処理説明が JSDoc 形式になっている箇所を `//` へ直す
- 処理塊の間に必要な空行を入れる / 余分を詰める
- テストラベルの語尾ズレ「〜の場合」「〜したら」→「〜のとき」に揃える
- テストラベルの結果が体言止めで、動詞が一意に補えるとき（例「xxx の確認」→「xxx を確認する」）

### 提案に留める（内容の判断・推測が要る）

- コメントが自明な What の繰り返しになっている（削るか書き換えるかは意図次第）
- 「なぜ」が欠落している（理由を創作しない。指摘のみ）
- JSDoc に `@param` / `@returns` が無い（説明を創作せず、欠けている旨だけ指摘する）
- テストラベルに条件や結果が読み取れない（「正常系」「ケース1」など。中身を Read しても補えなければ提案に回す）

迷ったら修正せず提案に回す。意味を変える書き換えは勝手に適用しない。

## 出力フォーマット

```
## 自動修正

- <ファイルパス>: <件数>件（<直した種別を簡潔に>）

## 要確認（提案）

- <ファイルパス>[:L行番号] `<該当>`
  - 問題: <どの規約に反するか>
  - 提案: <どう直すか>
```

自動修正の差分は git で確認できる旨を添える。違反が無ければ「規約違反なし」と明記する。

## 注意

- 修正後はプロジェクトのフォーマッター / リンターを通す（コマンドは推測せず、分かる場合のみ促す）
- `describe` のグループ名、E2E / UI 描画テストは命名点検の対象外
- 提案部分は内容を創作して埋めない
