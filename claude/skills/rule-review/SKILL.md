差分が CLAUDE.md と共通ルール・設計方針に沿っているかに集中してレビューする。
網羅的なバグ探し・効率・簡素化はビルトイン `code-review`、コメント/テスト命名の体裁は `format-check` に委ねる。

## 差分の取得

レビュー対象は「作業中の変更」を主軸にする。

1. !`git status --short`
2. !`git diff --cached --stat`
3. !`git diff --stat`
4. !`git diff --cached`
5. !`git diff`

staged も unstaged も空なら、ブランチ全体差分にフォールバック:

- !`git diff --stat main...HEAD`
- !`git diff main...HEAD`

それでも差分がなければ、その旨を伝えて終了する。

## レビュー観点

以下の観点で差分をレビューし、問題があれば指摘する。問題なければ「問題なし」と明記する。

### 1. ルール準拠

プロジェクトの CLAUDE.md およびグローバル共通ルールへの違反をチェックする:

- 依存方向が一方通行か（UI → サービス → データアクセス、逆参照なし）
- 1ファイル 400 行 / 1関数 50 行の目安を大きく超えていないか
- 型が厳格か（any / as unknown 等の回避、型アノテーションの省略なし）
- 新しい依存を増やしていないか。増やすなら標準/既存で代替できない理由が示されているか
- 機密情報（API キー・トークン・パスワード・鍵）のハードコードや、ログ・出力への露出がないか
- 言語固有ルール（`rules/*.md`、例: SQL の CTE）は、プロジェクトが採用していれば併せて確認する

### 2. 設計・方針準拠

- 責務の分離は適切か（1つの関数/クラスが複数の責務を持っていないか）
- 既存のコードとパターンが統一されているか
- 不要な抽象化や過度な複雑さがないか
- 変更が目的のスコープに収まっているか（無関係なリファクタ・自動生成ファイルが混ざっていないか）

### 3. ロジック・セキュリティ（明白なもののみ）

- 明らかなロジック欠陥（null/undefined の未処理、off-by-one、エッジケースの考慮漏れ）
- インジェクション（SQL / XSS / コマンド）の可能性

網羅的なバグ/効率レビューは深追いせず、ビルトイン `code-review` に委ねる。

## 出力フォーマット

指摘はファイル単位でまとめ、以下の形式で出す:

```
## <ファイルパス>

- [重要度: 高/中/低] 指摘内容
  - 該当箇所: L行番号
  - 理由: なぜ問題か
  - 提案: どう直すか
```

最後に全体の総評を 1-2 文で書く。

## 役割分担

- 網羅的なバグ/効率/簡素化のレビュー: ビルトイン `code-review`
- コメント規約・テスト命名の体裁: `format-check`
- コードとドキュメントの内容齟齬: `docs-check`
- リポジトリ全体の俯瞰レビュー: `review-repo`
