テストコードから「何を保証しているか」の一覧（マトリクス）を生成し、`docs/TESTS.md` に書き出す。
コードが「どう動くか」を示すのに対し、このマトリクスは「何がテストで担保されているか」を一望する用途。

## 手順

### 1. テストファイルを列挙

プロジェクトの慣習に合わせてテストを探す（典型は `tests/**` / `**/*.test.ts` / `**/*.spec.ts` / `__tests__/**`）。

```bash
find . -path ./node_modules -prune -o \( -name "*.test.*" -o -name "*.spec.*" \) -print | sort
```

見つからなければ探索パターンを変えて再試行。それでも無ければ「テストが見つからない」と伝えて終了。

### 2. ケースを抽出

各ファイルの `describe` / `it` / `test` ラベルを階層ごと抽出する。

```bash
for f in $(対象ファイル); do
  echo "##### $f"
  grep -nE "(describe|it|test)\(" "$f" | sed -E "s/^[0-9]+:[[:space:]]*//"
done
```

ファイル別件数も取る（サマリ用）:

```bash
for f in $(対象ファイル); do printf "%-45s %s\n" "$f" "$(grep -cE "^\s*(it|test)\(" "$f")"; done
```

総数はテストランナーの出力を正とする（例 `pnpm test` / `npx vitest run` の "Tests N passed"）。grep の単純カウントとズレたら実行結果を採用する。

### 3. 種別を分類

各ケースを観点で分類する（ラベルと中身から判断）:

- **正常** … 期待入力での基本動作
- **境界** … 閾値・端点（最大長、空入力、切替条件など）
- **異常** … 不正入力に対するエラー／null・既定値返し
- **防御** … 壊れた入力でも crash しない・誤検出しない・上限/サニタイズなど堅牢性
- **不変条件** … 往復一致など property 的な保証

### 4. docs/TESTS.md を生成

`docs/` が無ければプロジェクトのドキュメント置き場に合わせる。構成:

1. 冒頭に用途の一文と実行コマンド（`pnpm test` 等、プロジェクトの実コマンドを確認して書く）
2. **サマリ表**: 層／モジュール／ファイル／件数、末尾に合計
3. **モジュール別マトリクス**: 1 行 = 1 ケース。列は `ケース` と `種別`
   - 層は依存順（下位 → 上位）に並べる
   - 各モジュールに「何を担うか」の一行説明を添える
   - テストラベルをほぼそのまま採録し、後でテストと照合・同期しやすくする

既に `docs/TESTS.md` があれば上書き再生成する（差分は git で確認できる）。

## 注意

- テストラベルは創作せず、実ファイルの記述を忠実に写す。要約しすぎてケースの意図を失わない。
- 種別はあくまで読み手の手がかり。迷うケースは中身（assert）を見て決め、それでも曖昧なら「正常」に寄せる。
- このスキルはドキュメント生成のみ。テストの追加・修正はしない。
